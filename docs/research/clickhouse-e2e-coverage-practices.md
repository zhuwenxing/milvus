## 结论

ClickHouse **已经做了测试 case → C++ 服务端源码区间的映射**，并用它为 PR 的 C++ 改动行推荐 stateless 测试。它的按 case 采集目前针对 `clickhouse-test` 执行的 **stateless SQL 测试**；Python/pytest integration 测试在另一条 LLVM 覆盖率流水线中贡献**聚合覆盖率**，从核查的配置中不能推断已获得 pytest case → C++ 行映射。[按 case 的 nightly 定义](https://github.com/ClickHouse/ClickHouse/blob/a4af999ad02217ea2c9ea4e2bd7f160b1a3fd120/ci/workflows/nightly_coverage.py) · [两类 CI job 配置](https://github.com/ClickHouse/ClickHouse/blob/a4af999ad02217ea2c9ea4e2bd7f160b1a3fd120/ci/defs/job_configs.py) · [pytest integration 说明](https://github.com/ClickHouse/ClickHouse/blob/a4af999ad02217ea2c9ea4e2bd7f160b1a3fd120/tests/integration/README.md)

## 已核实的按 case 采集链路

1. **构建和调度。** `WITH_COVERAGE=ON` 用 Clang `-fprofile-instr-generate -fcoverage-mapping` 插桩；`WITH_COVERAGE_DEPTH=ON` 打开服务端按测试采集代码。NightlyCoverage 每日 02:13 UTC 在主分支构建带插桩的 `clickhouse` 二进制产物，再放入 stateless-test 容器运行 8 个分片；构建 job 使用 binary-builder 容器，但覆盖率产物本身是二进制，不是专用服务端镜像。2026-09-24 的 [8 个分片均显示 success](https://github.com/ClickHouse/ClickHouse/actions/runs/35947720166)。[CMake flags](https://github.com/ClickHouse/ClickHouse/blob/a4af999ad02217ea2c9ea4e2bd7f160b1a3fd120/cmake/sanitize.cmake#L156-L196) · [构建参数](https://github.com/ClickHouse/ClickHouse/blob/a4af999ad02217ea2c9ea4e2bd7f160b1a3fd120/ci/jobs/build_clickhouse.py#L31-L32) · [nightly workflow](https://github.com/ClickHouse/ClickHouse/blob/a4af999ad02217ea2c9ea4e2bd7f160b1a3fd120/ci/workflows/nightly_coverage.py) · [job 配置](https://github.com/ClickHouse/ClickHouse/blob/a4af999ad02217ea2c9ea4e2bd7f160b1a3fd120/ci/defs/job_configs.py#L157-L177)
2. **隔离 case 窗口。** 该模式将测试 runner 设为单 worker，并加 `--collect-per-test-coverage`。`clickhouse-test` 在每个 case 前执行 `SYSTEM SET COVERAGE TEST '<case>'`，结束后执行空名字命令以冲刷最后一个 case。服务端 `setCoverageTest()` 在切换时读取上一个 case 的计数器，调用 `__llvm_profile_reset_counters()`，然后更新当前 case 名。这里没有声称能排除服务端后台线程的命中。[runner 配置](https://github.com/ClickHouse/ClickHouse/blob/a4af999ad02217ea2c9ea4e2bd7f160b1a3fd120/ci/jobs/functional_tests.py#L625-L666) · [case 入口](https://github.com/ClickHouse/ClickHouse/blob/a4af999ad02217ea2c9ea4e2bd7f160b1a3fd120/tests/clickhouse-test#L4185-L4198) · [最终 flush](https://github.com/ClickHouse/ClickHouse/blob/a4af999ad02217ea2c9ea4e2bd7f160b1a3fd120/tests/clickhouse-test#L6996-L7003) · [计数器切换](https://github.com/ClickHouse/ClickHouse/blob/a4af999ad02217ea2c9ea4e2bd7f160b1a3fd120/base/base/coverage.cpp#L359-L409)
3. **转成服务端代码位置。** 服务端把 LLVM counter 与自身 ELF 中的 coverage mapping 对应，保留 `(file, line_start, line_end)`；写入 `system.coverage_log`，其中有 `test_name`、源码区间、`min_depth`、`branch_flag`。另有间接调用记录表。当前文档澄清 `min_depth` 实际是 LLVM 函数进入次数，**不是调用深度**；精确调用深度的 XRay 开关是可选的。[server SQL 入口](https://github.com/ClickHouse/ClickHouse/blob/a4af999ad02217ea2c9ea4e2bd7f160b1a3fd120/src/Interpreters/InterpreterSystemQuery.cpp#L1256-L1289) · [coverage mapping 与写表](https://github.com/ClickHouse/ClickHouse/blob/a4af999ad02217ea2c9ea4e2bd7f160b1a3fd120/src/Common/CoverageCollection.cpp#L29-L92) · [建表](https://github.com/ClickHouse/ClickHouse/blob/a4af999ad02217ea2c9ea4e2bd7f160b1a3fd120/tests/clickhouse-test#L6676-L6711) · [字段解释](https://github.com/ClickHouse/ClickHouse/blob/a4af999ad02217ea2c9ea4e2bd7f160b1a3fd120/ci/jobs/scripts/test_selection.md)
4. **持久化和校验。** 分片结束后把本地 `system.coverage_log` 导出到 CI 数据库 `checks_coverage_lines`，随后用**生产查询及评分器**验证刚导出的数据至少能找到一条可用的源码区间；空结果或校验失败会使导出失败。[导出器](https://github.com/ClickHouse/ClickHouse/blob/a4af999ad02217ea2c9ea4e2bd7f160b1a3fd120/ci/jobs/scripts/functional_tests/export_coverage.py#L60-L104)

## 如何使用覆盖率

- **变更驱动选测。** 选择器从 PR diff 的 C++ 改动行出发，查 `checks_coverage_lines` 中覆盖这些行的 case；限定源码区间宽度 ≤40 行、同一区间的测试拥有者 ≤150，按 `1 / (区间宽度 × 拥有者数量)` 为命中排序。改动的测试及该 PR 先前失败的测试强制纳入，选测结果及证据写入 `stateless-selection.json`。这服务于相关性排序，不能等同于断言质量。[查询和评分](https://github.com/ClickHouse/ClickHouse/blob/a4af999ad02217ea2c9ea4e2bd7f160b1a3fd120/ci/jobs/scripts/coverage_selection.py#L132-L296) · [配置](https://github.com/ClickHouse/ClickHouse/blob/a4af999ad02217ea2c9ea4e2bd7f160b1a3fd120/ci/jobs/scripts/test_selection_config.py) · [manifest](https://github.com/ClickHouse/ClickHouse/blob/a4af999ad02217ea2c9ea4e2bd7f160b1a3fd120/ci/jobs/scripts/test_selection_manifest.py)
- **独立的聚合覆盖率。** 另一个 `amd_llvm_coverage` 构建会运行 stateless、Python/pytest integration 和 UT 分片；合并各分片 `.profdata`，导出 LCOV、HTML、PR diff 报告。该流程检查分片完整性，缺一片不发布看似完整的报告。这是**整套测试的覆盖率**，不能反查“某个 pytest case 覆盖了哪一行”。[integration coverage jobs](https://github.com/ClickHouse/ClickHouse/blob/a4af999ad02217ea2c9ea4e2bd7f160b1a3fd120/ci/defs/job_configs.py#L1379-L1398) · [完整性检查](https://github.com/ClickHouse/ClickHouse/blob/a4af999ad02217ea2c9ea4e2bd7f160b1a3fd120/ci/jobs/llvm_coverage_job.py#L367-L404) · [LCOV/HTML 生成](https://github.com/ClickHouse/ClickHouse/blob/a4af999ad02217ea2c9ea4e2bd7f160b1a3fd120/ci/jobs/scripts/merge_llvm_coverage.sh)

## 成熟度与 Milvus 可借鉴处

ClickHouse 的 [选测设计文档](https://github.com/ClickHouse/ClickHouse/blob/a4af999ad02217ea2c9ea4e2bd7f160b1a3fd120/ci/jobs/scripts/test_selection.md) 明确写出当前边界：使用最近 14 天的快照，要求 8 个分片均有 72 小时内的数据；扩展选测矩阵仍关闭，60–90 天的回放质量门槛和各配置重复测试预算尚未验证。因此可把它视为**运行中的按 case 覆盖采集及有限范围的选测**，不能说它已经验证了大范围自动选测的漏测率。其 [`SelectionConfig`](https://github.com/ClickHouse/ClickHouse/blob/a4af999ad02217ea2c9ea4e2bd7f160b1a3fd120/ci/jobs/scripts/test_selection_config.py) 也保留这些门槛。

**对 Milvus 的推论：**现有 Go+C++ 插桩镜像已证明能得到单个 Python client case 的服务端代码映射。若进一步产品化，优先做与 ClickHouse 对应的三件事：① 将 case ID、精确源码区间、服务端 commit、快照时间和分片身份持久化；② 每次采集后用同一条生产查询做 canary，并拒绝缺片或过期数据；③ 先以 PR 改动行给出测试推荐和证据，再用历史故障回放验证漏测率。ClickHouse 的 stateless 单 worker 流程不能直接证明 Milvus 多组件服务端在单 case 窗口内没有后台覆盖污染，这是 Milvus 需要单独评估的工程问题。
